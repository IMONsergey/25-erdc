# Интеграция карты ИСУП в 25 ERDC

## Рекомендуемая архитектура

Для сайта `25-erdc` выбран отдельный маршрут `/map-lab/` как независимый Vite entry point. Главная страница не меняется, OpenLayers и большой набор геоданных грузятся только на лабораторной странице.

Текущая реализация использует три режима:

- `mock`: публичный режим GitHub Pages. Сейчас это не выдуманные данные, а статический snapshot ИСУП от 18 августа 2026: 1753 объекта, 22 мастер-плана, 12 отраслей.
- `remote`: прямое чтение штатных API/WFS из браузера, если CORS и авторизация разрешены для домена нашего сайта.
- `proxy`: будущий BFF/backend, если потребуется серверная авторизация, нормализация, кеширование или объединение API.

## Почему iframe не подходит

Iframe быстро вставит текущую карту, но плохо решит основную задачу:

- визуальный язык ИСУП не совпадает с текущим сайтом 25 ERDC;
- сложно синхронизировать выбранный город, фильтры и карточки с остальными блоками сайта;
- Basic/session-авторизация и WAF остаются внутри iframe;
- SEO, аналитика и доступность будут ограничены;
- мобильная bottom sheet логика будет конфликтовать с layout родительской страницы.

Iframe можно оставить только как временный внутренний fallback для сверки с оригиналом.

## Возможность прямого подключения API

GeoServer WFS можно читать напрямую технически: `access-control-allow-origin: *` наблюдался, а WFS без Basic Auth вернул полный набор точек. Основные справочники `isup.erdc.ru/api/geometry/public/showcase/*` в наблюдаемом ответе не показывали CORS allow-origin, поэтому для GitHub Pages прямой live-режим может быть частичным.

Если коллеги разрешат CORS для `https://imonsergey.github.io` или будущего production-домена, `remote` можно включать без BFF для публичных данных.

## Нужен ли BFF

BFF нужен, если:

- API останется под Basic/session-авторизацией;
- нужно скрывать credentials;
- нужно объединять справочники ИСУП и WFS в один контракт;
- нужно кешировать данные и защищаться от частых bbox/search-запросов;
- нужно фильтровать поля перед публичной публикацией;
- появятся приватные карточки, изображения или права доступа.

Для текущей публичной версии BFF не разворачивался: GitHub Pages использует статический snapshot без секретов.

## Схема авторизации

Текущий demo-доступ используется только локально при аудите. Его нельзя хранить во frontend, `.env`, GitHub Actions или dist. Для production есть два безопасных варианта:

- открыть публичные read-only endpoints с CORS allowlist;
- держать credentials на BFF и отдавать сайту только очищенный read-only контракт.

## Нормализация данных

ИСУП WFS FeatureCollection приводится к внутренней модели:

- `planId` из `dkp_id`;
- `industryId` и `industryName` из отраслевых fields;
- `stageId` в первую очередь из `obj_current_stage_key`; `obj_stage_*_status` остаются дополнительными полями для сверки;
- `title` из `obj_name`;
- `address` из `obj_description`/городских полей;
- `deadline` из плановой или проектной даты;
- `budget` из `budget_approved_total`;
- `coordinates` из GeoJSON geometry.

Адаптер лежит в `src/map-lab/isupAdapter.js`, provider-слой в `src/map-lab/mapData.js`.

## Работа с картой

Прототип использует OpenLayers, как исходная карта ИСУП. На `/map-lab/` реализованы:

- zoom и drag мышью/touch;
- выбор маркера на карте;
- выбор объекта в списке;
- синхронизация выбранного объекта со списком и картой;
- кластеры на дальнем масштабе;
- отдельный polygon layer зоны влияния;
- переключение слоёв;
- поиск с debounce;
- фильтры по стадиям, отраслям и мастер-планам;
- loading, empty и error states;
- desktop sidebar и mobile bottom sheet.

## Этапы миграции

1. Snapshot-прототип: готово. Сложность низкая, данные обновляются вручную или скриптом.
2. Прямой `remote` read-only режим: средняя сложность. Нужны CORS-правила и подтверждённый стабильный API.
3. BFF/proxy: средняя сложность. Нужны hosting backend, кеш, секреты вне frontend и мониторинг ошибок.
4. Полная интеграция с карточками/медиа: высокая сложность. Нужны endpoints карточек, изображений, права доступа и правила публикации.
5. Замена текущего блока проектов на production-карту: высокая сложность. Нужны дизайн-ревью, перформанс-бюджет и договорённость по источнику истины.

## Зависимости от команды ИСУП

- Подтвердить, что WFS `isup:object_showcase_point` является стабильным публичным read-only контрактом.
- Дать OpenAPI или описание `showcase` endpoints.
- Дать список допустимых публичных fields.
- Подтвердить CORS-политику для production-домена 25 ERDC.
- Уточнить, можно ли публично использовать WMS `erdc:azrf_dfo.osm.wms` или нужна отдельная подложка.
- Дать правила обновления snapshot: периодичность, webhooks, дата актуальности.
- Дать endpoint карточки объекта и медиа, если он есть.
- Подтвердить соответствие стадий `obj_stage_*_status` бизнес-логике.

## Что сейчас mock

Данные объектов и классификаторы уже взяты из ИСУП snapshot. Mock-часть остаётся только в инфраструктурном смысле: GitHub Pages не делает live-запросы к ИСУП. Изображения карточек пока используют локальные ассеты сайта 25 ERDC по отраслевой эвристике, потому что отдельный стабильный media endpoint объекта не подтверждён.
